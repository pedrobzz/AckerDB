---
title: "Custom Credential Verifiers"
description: "Integrate an application-owned credential verification module."
---

Use a custom credential verifier when your application owns bearer-token
verification and OIDC is not the right authority. The verifier is one
server-side module with a default export that satisfies
"CredentialVerifier"; configure it once for the application.

## Configure the module

Point ".ackerdb.config.json" at a module relative to the server application:

~~~json title=".ackerdb.config.json"
{
  "credentialVerifier": "./auth/verifier.ts"
}
~~~

"credentialVerifier" and "oidc" are mutually exclusive. With neither
configured, anonymous credentials work and external bearer credentials fail
closed. Credentials issued by AckerDB's built-in credential vault continue to
authenticate.

## Return verified credential evidence

The module default export must provide "verify", "revocationBound", and
"subscribeInvalidation":

~~~ts title="auth/verifier.ts"
import {
  unauthenticated,
  type CredentialVerifier,
  type PrincipalInvalidation,
  type VerifiedCredential,
} from "@ackerdb/server";

const listeners = new Set<(event: PrincipalInvalidation) => void>();

const verifier = {
  revocationBound: {
    kind: "invalidation",
    deadlineMs: 5_000,
  },

  async verify(token: string): Promise<VerifiedCredential> {
    const session = await verifyOurSessionToken(token);
    if (session === null) throw unauthenticated();

    return {
      kind: "user",
      issuer: "https://auth.example.com",
      subject: session.accountId,
      claims: {
        plan: session.plan,
      },
      expiresAt: session.expiresAt.getTime(),
      tokenId: session.id,
    };
  },

  subscribeInvalidation(listener: (event: PrincipalInvalidation) => void) {
    listeners.add(listener);
    return () => listeners.delete(listener);
  },
} satisfies CredentialVerifier;

export default verifier;
~~~

Return either:

| Kind | Required evidence |
| --- | --- |
| "user" | issuer, subject, claims, expiration, and token ID or null |
| "workload" | issuer, subject, claims, expiration, and token ID or null |

A user credential is cryptographic or application-owned evidence, not yet an
application Identity. AckerDB maps its issuer and subject to a durable user
Identity and resolves its scopes. Do not return an "identity" field from the
verifier. A workload credential deliberately has no user Identity.

"claims" should be the validated, bounded data a Function needs for
authorization. It becomes immutable on the verified principal. Do not put a
raw bearer token, unvalidated payload, or secret in claims.

## Distinguish invalid from unavailable

Call "unauthenticated()" for an invalid, expired, malformed, revoked, or
otherwise unacceptable token. A plain thrown error or rejected promise is
treated as "auth_unavailable", so it signals that verification infrastructure
could not currently decide rather than that a user supplied bad credentials.

This distinction matters to clients: unauthenticated credentials require
replacement; auth-unavailable can be retried under the client's bounded
connection policy.

## Declare the revocation guarantee

Use one of the two "revocationBound" shapes:

~~~ts
{ kind: "token-expiration" }
~~~

Use it only when token expiration is the bound on authority and there is no
earlier revocation signal. Otherwise use:

~~~ts
{ kind: "invalidation", deadlineMs: 5_000 }
~~~

For an invalidation-bound verifier, call every listener with the narrowest
known invalidation when token authority, account authority, or relevant grant
changes:

~~~ts
function revokeToken(issuer: string, tokenId: string) {
  for (const listener of listeners) {
    listener({ issuer, tokenId });
  }
}

function disableAccount(issuer: string, subject: string) {
  for (const listener of listeners) {
    listener({ issuer, subject });
  }
}
~~~

An invalidation can name issuer alone, issuer plus subject, or issuer plus
token ID. The subscription function must return a cleanup function; AckerDB
uses it to release authentication leases. Keep invalidation synchronous and
small: it is the signal that makes live sessions re-authorize rather than a
place to perform slow verification work.

## Resolve scopes separately

The verifier proves external credential evidence. Application role and
entitlement lookup belongs in an optional "scopeResolver" module, not in a
duplicate access decision inside "verify":

~~~json
{
  "credentialVerifier": "./auth/verifier.ts",
  "scopeResolver": "./auth/scopes.ts"
}
~~~

The resolver's grant is re-read on credential verification and authentication
transition. If its backing entitlement changes, coordinate it with the
verifier's invalidation path so live sessions cannot retain old authority.
Read [Scopes](/docs/scopes) for grant shape and [Access Policies](/docs/access-policies)
for per-operation authorization.
