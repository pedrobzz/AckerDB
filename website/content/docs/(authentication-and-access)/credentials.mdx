---
title: "Credentials"
description: "Connect anonymous, bearer, and source-driven client credentials."
---

Every client connection presents one explicit credential. AckerDB supports two
wire credential kinds:

| Client credential | Server result |
| --- | --- |
| `{ kind: "anonymous" }` | The anonymous principal. No verifier runs. |
| `{ kind: "bearer", token }` | A verifier must accept the token as a user or workload principal. |

"AckerDBClient" and its WebSocket transport do not infer an omitted
credential as anonymous. Configure a client with anonymous, a fixed bearer
token, or an application-owned credential source. An HTTP request that reaches
an HTTP handler without an "Authorization" header is explicitly represented as
the anonymous principal.

## Use an anonymous credential for public work

Public Functions can be called with the explicit anonymous credential:

~~~ts
import { AckerDBClient } from "@ackerdb/client";

const client = new AckerDBClient({
  url: "https://api.example.com",
  credential: { kind: "anonymous" },
});
~~~

Anonymous callers can only pass declarations whose access policy allows them.
An "authenticated" Function, scope requirement, or policy that rejects the
anonymous principal returns an unauthenticated outcome.

## Use a fixed bearer credential

Use a fixed bearer when the token is stable for the client lifetime:

~~~ts
const client = new AckerDBClient({
  url: "https://api.example.com",
  credential: {
    kind: "bearer",
    token: accessToken,
  },
});
~~~

The server verifies the token at the connection handshake and confirms a
secret-free authentication descriptor. A user descriptor contains a durable
AckerDB Identity and credential provenance; a workload descriptor contains
provenance but no user Identity. Both include a credential lifetime disclosure
when the credential expires.

Do not treat client-side token parsing as authorization. The accepted
principal is the server's verified descriptor and the Function handler sees
the full verified principal as "ctx.auth".

## Let a source own token refresh

Use "credentialSource" when an identity SDK can refresh, sign out, or switch
accounts while the application remains mounted:

~~~ts
const client = new AckerDBClient({
  url: "https://api.example.com",
  credentialSource: async () => {
    const token = await identity.getAccessToken();
    return token === null
      ? { kind: "anonymous" }
      : { kind: "bearer", token };
  },
});
~~~

The client calls the source before the initial connection, before the
server-disclosed credential lifetime ends, after a principal rejection, and
when "refreshCredential()" is called without an argument. Concurrent source
triggers are coalesced; failed or timed-out source calls retry with bounded
backoff rather than spinning.

Exactly one of "credential" and "credentialSource" is required. A source owns
credential replacement: passing a credential to "refreshCredential" on a
source-backed client is a configuration error.

## Rotate a connected principal

On a fixed-credential client, present a new credential with
"refreshCredential". Presenting anonymous is the protocol sign-out.

~~~ts
await client.refreshCredential({
  kind: "bearer",
  token: await identity.getAccessTokenOrThrow(),
});

await client.refreshCredential({ kind: "anonymous" });
~~~

The promise resolves only after the server confirms the new principal and
auth epoch. Existing live Queries, Channels, and realtime sessions are
re-authorized around that boundary; they must not be assumed valid under the
previous principal.

In React, use useAuthentication. [React API](/docs/react-api) owns the hook
surface, and [Client Lifecycle](/docs/client-lifecycle) owns its state model.

For a source-backed provider, refresh re-invokes the source. Sign out at the
identity provider first, then refresh AckerDB so the source returns the
anonymous credential.

## Respond to rejection honestly

A rejected or expired bearer moves the client to
"authentication-blocked" and authentication to "refresh-required". The
client stops reconnecting until a fixed credential is refreshed; a
credential-source client retries source acquisition with its bounded policy.
Read these states through [Client Lifecycle](/docs/client-lifecycle) instead
of retrying calls against a connection that cannot authenticate.

Configure the server-side verifier with [OIDC](/docs/oidc) or a
[Custom Credential Verifier](/docs/custom-credential-verifiers). Authorization
after authentication belongs in [Access Policies](/docs/access-policies) and
[Scopes](/docs/scopes).
