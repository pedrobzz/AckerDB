  the feature is stable. Use them only where you can update alongside AckerDB.
</Warning>

Files are stored outside normal table data. The application first creates a
bounded upload session, the client uploads bytes to that session, and trusted
application code later claims the resulting file or issues it a grant. This
keeps large request bodies out of mutation execution and gives abandoned
uploads a finite lifetime.

## Upload from a client

Declare a mutation that creates an upload session. The generated File API
validates the requested size, content type, checksum, expiry, and owner before
returning a session-bound upload URL.

~~~ts title="functions/avatars.ts"
import { v } from "@ackerdb/server";
import { mutation } from "@workspace/ackerdb-generated/server";

export const createAvatarUpload = mutation({
  access: "authenticated",
  args: {
    size: v.int().min(1),
    contentType: v.string(),
    sha256: v.string(),
  },
  handler: async (ctx, args) =>
    ctx.files.createUploadSession({
      maxBytes: args.size,
      contentTypes: [args.contentType],
      expectedSha256: args.sha256,
      expiresIn: "10m",
    }),
});
~~~

Use the client helper with a browser File, Blob, or byte buffer. It calls the
mutation, sends the required PUT request, and returns the file ID after a
successful upload.

~~~ts title="client"
import { api } from "@workspace/ackerdb-generated/api";

const result = await client.files.upload({
  createSession: api.avatars.createAvatarUpload,
  args: {
    size: file.size,
    contentType: file.type,
    sha256,
  },
  file,
});

if (!result.ok) throw result.error;
const fileId = result.data;
~~~

The upload endpoint requires an exact Content-Length and verifies the declared
limits. Repeating the same successful upload session is safe: it returns the
same file ID rather than storing a second object. A session defaults to one
hour and cannot last longer than one hour. Files begin in the pending state;
claiming them or issuing a grant activates them. Pending files that are never
claimed are cleaned up after their limited lifetime.

## Store bytes from trusted procedures

A procedure can stream server-side bytes without exposing an upload URL. Give
the exact byte count and, when available, the expected digest.

~~~ts title="functions/imports.ts"
import { procedure } from "@workspace/ackerdb-generated/server";

export const importAsset = procedure({
  access: "system",
  args: {},
  handler: async (ctx) => {
    const response = await fetch("https://assets.example.com/logo.png");
    const length = response.headers.get("content-length");
    if (response.body === null || length === null) {
      throw new Error("asset response needs a known body length");
    }
    const size = Number(length);
    if (!Number.isSafeInteger(size) || size < 0) {
      throw new Error("asset response has an invalid body length");
    }

    return ctx.files.store(response.body, {
      size,
      name: "logo.png",
      contentType: "image/png",
    });
  },
});
~~~

Procedure code must use a finite, trusted size. The runtime bounds the stream
to that size and rejects a mismatch. Use ctx.files.open for streaming reads or
ctx.files.bytes only when an explicit maximum makes buffering safe.

## Download with a grant

Do not place raw object-store paths in application responses. Create a
[File Grant](/docs/file-grants) and let the client fetch its URL. For a public
bearing grant, ordinary fetch is sufficient. For authenticated or validated
grants, use client.files.fetch so the configured server origin and
Authorization header are preserved.

File metadata contains the name, size, content type, SHA-256 digest, owner,
and lifecycle state—not the uploaded bytes. Deleting a file revokes every
grant and queues its physical bytes for cleanup.

## Limits and state

The default deployment limit is 1 GiB per file and the hard limit is 5 GiB.
Set a smaller maxBytes on an upload session whenever the product contract
permits it. A client-provided filename and content type are metadata; enforce
your own product policy before trusting them for display or processing.

For backend setup, see [Local File Storage](/docs/local-file-storage) or
[S3 File Storage](/docs/s3-file-storage).
