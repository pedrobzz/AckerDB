# Queues design continuation

## Purpose

Continue designing a durable Queue plugin for AckerDB. The Queue should let server
code enqueue an ordinary procedure transactionally and optionally wait for its
durable outcome, while an AckerDB-owned logical consumer executes jobs
asynchronously through the normal procedure machinery.

AgentDB is intentionally out of scope: it uses a separate disposable-snapshot
and isolated-process architecture captured in the adjacent AgentDB handoff.

## Decisions reached

- Queue semantics belong in a plugin: its private schema, job state machine,
  leases, retries, results, cancellation, dispatcher, and public capabilities
  should live in a future Queue package rather than in AckerDB core.
- A Queue "worker" is a logical dispatcher/consumer, not a Bun Worker or child
  process. Job procedures are trusted application code and should run through
  AckerDB's ordinary procedure machinery so HTTP, `ctx.tx(...)`, admission,
  publication, and shutdown retain one implementation.
- Enqueue is transactional. A committed enqueue is durable; a rolled-back
  enqueue must never become executable.
- Waiting is optional and procedure-only. Prefer `ctx.jobs.wait(job, options)`
  over a stateful `job.wait(...)` method. A wait timeout or abort stops only the
  waiter, not the durable job.
- Cancellation is explicit (`ctx.jobs.cancel(job)` or equivalent); it must not
  be coupled to `wait` cancellation.
- Persist a stable `ProcedureRef` address plus validated/encoded arguments, not
  a JavaScript function object. [`packages/core/src/refs.ts`](../../packages/core/src/refs.ts)
  defines references as typed opaque addresses and `getRef(...)` as their
  runtime extraction boundary.
- Queue execution is at least once. Exactly-once external effects are not a
  credible promise; job procedures must be idempotent or use their job ID as an
  idempotency key where the downstream system supports one.

## Desired application surface

The current preferred shape is:

```ts
const job = await ctx.tx((tx) =>
  tx.jobs.enqueue(api.reports.generateReport, args),
);

const result = await ctx.jobs.wait(job, {
  signal: ctx.abortSignal,
  timeoutMs: 30_000,
});
```

`enqueue` returns a small serializable `JobRef<Result>` carrying the queue mount
and durable job ID (plus only phantom result typing). `wait` reads the durable
terminal result. It should use read-register-recheck around an in-memory waiter
to close the completion race, then unregister on success, timeout, abort, or
shutdown. It should not continuously poll.

The target must be a procedure, not a mutation callback or raw function. Queue
configuration or enqueue validation must prove that the reference exists and
has kind `procedure`. Retry, delay, priority, and retention APIs remain open.

## Runtime shape

```text
application transaction
  -> Queue plugin enqueue (private durable row)
  -> ordered post-commit wakeup
  -> Queue dispatcher under its own execution root
  -> atomic claim with a fenced lease
  -> ordinary AckerDB procedure invocation
  -> HTTP and/or ctx.tx(...) as usual
  -> durable SUCCEEDED / retryable AVAILABLE / terminal FAILED
  -> post-commit notification to in-memory waiters
```

The dispatcher must have bounded concurrency, bounded claim batches, and an
indexed next-due lookup. When idle it should sleep until a commit wakeup or the
next known `availableAt`/lease-expiry deadline; a permanent polling loop would
violate AckerDB's idle-cost rule. On a wakeup it must always re-read durable state,
because notifications are hints rather than truth.

The private job schema will likely need a durable ID, procedure address,
encoded arguments, state (`AVAILABLE`, `RUNNING`, `SUCCEEDED`, `FAILED`,
`CANCELED`), attempt and `availableAt`, lease/fencing identity, bounded terminal
outcome, timestamps, and possibly a running-attempt cancellation request.

Use exact names only after domain modeling. Avoid a separate `RETRY` state if
`AVAILABLE + availableAt` represents the invariant without another branch.

## Delivery and failure invariants

1. Claim is one atomic private-schema transaction. It selects only due work or
   an expired lease and installs a new lease plus fencing token.
2. Long jobs renew their lease. Completion is accepted only for the current
   `(jobId, attempt, leaseOwner/fencingToken)`, so a stale executor cannot
   overwrite a newer attempt after losing its lease.
3. A process crash after the job's external effect but before terminal commit
   causes a retry and possible duplicate effect. Preserve this fact in the API
   and documentation; do not hide it behind an "exactly once" label.
4. Persist terminal outcome before waking waiters. An in-memory notification
   can be lost; the durable row cannot.
5. Results, retention, admission, claims, and retries have finite budgets;
   saturation yields typed backpressure instead of unbounded queues or storms.
6. Backoff is one declared policy. Distinguish retryable dependency failure
   from validation, authorization, and deterministic application failure.

Cancellation must distinguish states:

- Before claim: atomically move the job to `CANCELED` and never execute it.
- While running: record cancellation durably, signal the active procedure
  best-effort, and resolve cancel-vs-complete by one defined race rule.
- After an executor disappears: recovery honors the durable cancel request.
- Cancellation cannot retract a completed transaction or external HTTP side
  effect. If the outcome is ambiguous, report ambiguity rather than claiming
  that the work was undone.

## Authority boundary

A durable job cannot retain the enqueue request's ambient async context or
live credential lease. The Queue dispatcher must run under its own execution
root, consistent with the definition in [`CONTEXT.md`](../../CONTEXT.md) and
the scheduling-boundary rule in
[`docs/adr/0002-reactive-execution-root.md`](../adr/0002-reactive-execution-root.md).

Recommended starting contract: queued targets are ordinary procedures with
`access: "system"`, invoked under AckerDB's system principal. If a job acts for a
user or tenant, application code passes the durable identity/tenant key as a
validated argument and the target rechecks live authorization and invariants.
Never persist bearer tokens merely to recreate the enqueuer's context.

Decide explicitly whether Queue may invoke only system procedures or needs a
narrower delegated principal. Default to system-only; a request credential
does not remain valid merely because the job outlives the request.

## Is this possible as a plugin with no AckerDB changes?

**Not with the current runtime API.** The Queue feature should be plugin-owned,
but the present AckerDB plugin boundary lacks the generic infrastructure needed
for autonomous durable work.

What already fits:

- A plugin mutation participates in the caller's transaction and receives a
  writer scoped to the plugin's private schema, so transactional `enqueue`
  fits the current model.
- A plugin procedure has `abortSignal` and `ctx.tx(...)`, so caller-owned
  `wait`, status, and cancellation capabilities fit the current model.
- Plugin lifecycle already gives correct startup order, shutdown cancellation,
  reverse-order cleanup, and a place to own a dispatcher resource.

What is missing:

1. [`PluginLifecycleContext`](../../packages/server/src/plugins/definition.ts)
   currently exposes only `mount` and `abortSignal`. It cannot open a private
   transaction after startup, so a lifecycle-owned dispatcher cannot scan,
   claim, renew, or complete jobs on its own.
2. Application procedures deliberately cannot be called in-process directly;
   their callable wrapper throws because they exist at the transport boundary.
   The runtime has procedure lookup and execution, but a plugin has no narrow
   capability to validate and invoke a stored `ProcedureRef` through that
   machinery.
3. A transactional plugin invocation has no commit-safe hook for waking
   lifecycle-owned work. Durable scans recover correctness, but low-latency,
   near-zero-idle dispatch needs an ordered handoff rather than polling.

Therefore the likely minimal AckerDB work is generic, not Queue-specific:

- a **plugin execution root** for AckerDB admission/shutdown and
  transactions against only that mount's private schema;
- a **runtime-owned procedure invocation capability** that resolves an
  explicitly supplied `ProcedureRef`, validates its kind/arguments/access,
  invokes it under an explicit principal, and returns its typed outcome without
  routing through loopback HTTP;
- a commit-safe wakeup if that cannot be encapsulated by the execution root.

Keep these least-authority: lifecycle code gets no application root `db`; only
the resolved job target gets an application `ProcedureCtx`. Reject loopback
HTTP, ambient registry access, permanent polling, and manual `.handler` calls.

This changes the verdict on the initial assumption:

- **Queue product/domain implementation:** 100% plugin.
- **Current AckerDB infrastructure:** requires a small generic extension before
  that plugin can autonomously execute jobs correctly.
- **Queue-specific scheduler/state machine in core:** not justified.

The plugin-isolation constraints that this must preserve are documented in
[`docs/adr/0005-plugins-are-isolated-capabilities.md`](../adr/0005-plugins-are-isolated-capabilities.md).

## Startup, recovery, and shutdown

On startup, scan an indexed, bounded batch of due jobs and expired leases, then
arm the next deadline. Durable state reconstructs lost wakeups and waiters.

On graceful shutdown:

1. Stop claiming, then abort or drain active procedures to the runtime deadline.
2. Commit only known outcomes that still own their fencing token.
3. Leave uncertain attempts leased for recovery after expiry.
4. Abort in-memory waiters without changing their durable jobs.

For multi-process AckerDB, wakeups are local hints and the durable due/lease index
remains authoritative; never rely on one in-memory bus for correctness.

The alpha has no plugin migration API: an unsafe private-schema change requires
operator-approved reset. Queue rows are source-of-truth work, so reset means
deliberate job loss, not cache eviction. See
[`docs/adr/0005-plugins-are-isolated-capabilities.md`](../adr/0005-plugins-are-isolated-capabilities.md).

## Questions for the next session

1. Design the narrowest plugin execution root: lifecycle capability or a
   declared background service bound by AckerDB after startup?
2. Factor procedure invocation from HTTP response handling without making
   procedures freely callable from arbitrary procedures.
3. Decide the authority rule (recommended: system-only targets) and when target
   existence/kind is validated: application assembly, enqueue, or both.
4. Define the exact state transitions and the lease-renewal/fencing protocol,
   including cancel-vs-complete and shutdown-vs-complete races.
5. Define all budgets against AckerDB's default deployment envelope.
6. Decide whether ordered post-commit hook is needed or a root-owned condition
   signal plus durable recheck proves the same invariant.
7. Test rollback, crash ambiguity, lease expiry, stale completion, duplicates,
   lost wakeup, cancellation, restart, saturation, and shutdown.
