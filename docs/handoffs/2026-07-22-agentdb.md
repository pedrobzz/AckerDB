# AgentDB continuation handoff

> Historical handoff. Any release or benchmark instruction here is superseded
> by [Releases and protected branches](../releases.md).

## Purpose

Continue designing AgentDB as an AckerDB plugin that gives an agent bounded SQL
access to an explicitly granted, disposable subset of application data. This
records the current direction and remaining design work; no implementation has
started.

Queues are excluded because they use a different architecture and have their
own handoff.

## Agreed direction

AgentDB creates a **materialized, procedure-scoped SQLite snapshot**, not a
logical `VIEW` over the canonical database and not a full database clone.

1. Application code defines the snapshot against its schema.
2. A procedure explicitly grants access with its current `tx.db` and validated
   parameters.
3. AgentDB copies only permitted rows and columns while the source transaction
   provides a consistent read.
4. The source transaction ends before agent-generated SQL runs.
5. A child process receives only the disposable database and executes bounded,
   read-only SQL.
6. Procedure completion, failure, or abort destroys the snapshot.

Desired API shape:

```ts
export const userSnapshot = defineAgentSnapshot(schema, {
  parameters: { userId: v.id("users") },
  tables: {
    orders: {
      where: ({ row, parameters }) => row.userId.eq(parameters.userId),
    },
    orderItems: {
      through: { table: "orders", foreignKey: "orderId" },
    },
    menuItems: {
      access: "shared",
      columns: ["id", "name", "priceCents"],
    },
  },
});

await using snapshot = await ctx.tx((tx) =>
  userSnapshot.capture(tx.db, { userId: ctx.auth.identity }),
);

const rows = await ctx.agentDb.query(snapshot, {
  sql: "SELECT ...",
});
```

The schema supplies table, column, relationship, and validator information; it
does not grant runtime access. `capture(tx.db, parameters)` is the separate,
explicit authority grant. Do not give AgentDB ambient access to the canonical
database or its path. This preserves [ADR 0005](../adr/0005-plugins-are-isolated-capabilities.md).

The exact adapter between `SnapshotHandle` and `ctx.agentDb.query` remains
open. The handle should implement `Symbol.asyncDispose`, so `await using`
cleans up on normal return, early return, exception, and abort. Partial capture
failures must clean up before propagating.

## Snapshot definition

Do not assume every table has `userId`. The DSL must represent:

- directly owned rows filtered by a validated principal/tenant parameter;
- transitively owned rows reached through declared foreign keys;
- explicitly shared reference rows;
- excluded tables and redacted columns.

The definition is the source of truth for row selection, relationship closure,
projection/redaction, exposed SQL names, and snapshot indexes. Multi-tenant
applications may scope by `tenantId` or `workspaceId` instead of `userId`.

## Plugin versus AckerDB core

The AgentDB package/plugin should own:

- `defineAgentSnapshot(schema, definition)` and plan validation/compilation;
- extraction through the explicitly supplied `tx.db`;
- disposable SQLite materialization, indexes, and snapshot metadata;
- the opaque handle and async disposal;
- its dedicated child-process pool and IPC;
- SQL authorization, budgets, cancellation, result encoding, and recycling;
- lifecycle startup, drain, shutdown, and stale-file cleanup;
- AgentDB-specific telemetry and typed failures.

Existing AckerDB already provides consistent transactions and `tx.db` in
[`packages/server/src/app/functions.ts`](../../packages/server/src/app/functions.ts),
procedure cancellation, isolated plugin capabilities, and lifecycle ownership
in [`definition.ts`](../../packages/server/src/plugins/definition.ts) and
[`runtime.ts`](../../packages/server/src/plugins/runtime.ts).

There is no confirmed core change yet. Prototype using public `DbReader` first,
then verify two boundaries:

1. **Opaque resource plumbing:** can a mount-bound `SnapshotHandle` reach the
   validated `ctx.agentDb.query` capability without a forgeable arbitrary path
   or global registry? If not, consider the smallest generic AckerDB primitive for
   procedure-owned opaque resources.
2. **Bounded extraction:** can public readers stream/page selected rows into
   SQLite without retaining the full subset as JavaScript objects? If not and
   the cost is material, consider a generic bounded read-cursor primitive.

Do not expose the canonical SQLite path or weaken root-schema isolation for
convenience. Any core addition must strengthen a general ownership boundary,
not make AgentDB a disguised first-class feature.

## Child-process contract

Agent SQL is synchronous, untrusted work and must not execute on the AckerDB
server thread. The AgentDB plugin supervises child processes; a child does not
receive an ordinary AckerDB procedure context.

It receives only the disposable snapshot, one request or tightly bounded
session, and fixed limits. It must not receive the canonical database path,
`ctx.tx`, credentials, application/plugin capabilities, application modules,
or network authority. Killing a pathological query must not threaten AckerDB.

Use a dedicated AgentDB pool with bounded active processes, queued work/bytes,
and per-procedure concurrency. On shutdown, stop admission, abort active work,
kill unresponsive children, and remove owned files.

Enforce at least:

- read-only opening and one statement per request;
- denial of `ATTACH`, extensions, schema writes, and dangerous pragmas;
- a SQLite authorizer/allowlist and instruction/progress limit;
- wall timeout followed by forced process termination;
- child memory/CPU constraints where supported;
- maximum SQL, result rows/bytes, temporary storage, and error/output bytes;
- handle validation so a forged reference cannot open another file.

Canonical writes remain typed AckerDB tools/procedures that reauthorize against
live state. A snapshot can become stale immediately after capture. Include
`capturedAt`, source version/commit, definition identity/version, and explicit
truncation metadata. Prefer a typed budget failure over silently truncating
source data.

## Performance model

Capture cost is proportional to visible rows/bytes plus copied index builds.
Capacity roughly scales with:

```text
active procedures × average snapshot bytes × copies/indexes
```

Canonical tables need indexes for every ownership predicate and transitive
join. Missing tenant or foreign-key indexes can make each capture a global
scan. Copy only indexes that serve expected agent queries.

Hold the source read transaction only during selection/copy; never while the
model reasons or runs SQL, because a long reader can delay WAL checkpoints.
Prefer a temporary file for larger snapshots; allow in-memory storage only
below an explicit budget.

Before choosing limits, define visible rows/bytes, active procedures, queries
per snapshot, latency target, result size, and saturation behavior. Measure
source transaction duration and allocations as well as SQL latency. The old
vendor-comparison release benchmark mentioned when this handoff was written has
been superseded by the protected AckerDB base/head check in
[Releases](../releases.md).

## Open questions

1. How exactly is a handle bound to the correct mount without exposing paths?
2. Can `DbReader` extraction be incremental and allocation-bounded?
3. How does the DSL represent cycles, composite keys, nullable relationships,
   shared rows, and explicit indexes?
4. May one snapshot run several queries, and with what concurrency/session cap?
5. How are IDs, BigInts, timestamps, blobs, and nulls encoded losslessly?
6. Which row, byte, time, instruction, memory, and pool limits are defaults
   versus application configuration?
7. How are network denial and filesystem confinement enforced per platform?
8. How does a definition fail early after an incompatible schema change?
9. Keep snapshots non-cacheable and procedure-owned initially?

## Verification boundary

Prove that:

- direct, transitive, shared, excluded, and redacted policies do not leak data;
- the source transaction ends before SQL execution;
- all success, failure, abort, timeout, shutdown, and partial-capture paths
  dispose files and processes;
- forged handles, `ATTACH`, extensions, pragmas, and schema writes cannot
  escape the disposable database;
- pathological SQL cannot block AckerDB or starve unrelated requests;
- process-pool saturation returns a bounded typed outcome;
- snapshot consistency and subsequent staleness are explicit;
- source query plans use ownership/relationship indexes;
- plugin isolation from the root database remains intact.
