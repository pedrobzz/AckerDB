# MCP paired Hetzner benchmark evidence

This is reproducible same-host evidence for the first-class MCP change, not a
claim that the repository's frozen global performance gate passed. Six full
schema-v7 runs were retained. DBZZ completed every configured case in its
runtime-default, exporter, and disabled telemetry profiles in all six runs.
Convex and SpacetimeDB had measured subscription failures, so the runner
correctly persisted `validation.status = "failed"`, left
`performanceAcceptance.status = "not-evaluated"`, and exited nonzero only
after writing each record.

## Measured-failure semantics

Schema v7 records a typed failure at the canonical case identity instead of
inventing zero metrics. Attempted, completed, and failed requests must still
balance; cancellation and release are bounded; and a terminal system failure
records all unmeasured configured cases as failures before the parent reclaims
the process. Correctness-failed evidence is saved with performance explicitly
not evaluated, then the command exits failing. Broken accounting, case shape,
or telemetry integrity remains fatal because such output is not evidence.

The final record's six non-DBZZ failures were:

- Convex shared fixed-rate: 156 duplicate and 234 unexpected deliveries.
- Convex shared capacity 32: 117 duplicate and 234 unexpected deliveries.
- Convex shared capacity 50: 39 duplicate deliveries.
- Convex partitioned capacity 500: 98/100 writers opened; two one-second probe
  timeouts.
- SpacetimeDB shared fixed-rate: release timed out after 5 seconds.
- SpacetimeDB partitioned fixed-rate: not measured after that terminal release
  failure.

These failures are retained evidence; they are not reclassified, hidden, or
used to make a cross-vendor performance claim.

## Paired performance conclusion

The two identical-harness pre-MCP draws establish a range rather than treating
one p99 sample as truth. The final result is compared with that range and the
matched-order intermediate runs below:

| Runtime-default shared metric | Pre-MCP range | Before fast path | First fast path | Structural fast path | Final beyond slower baseline edge |
| --- | ---: | ---: | ---: | ---: | ---: |
| delivery p95 | 23.167-25.986 ms | 24.110 ms | 25.669 ms | 24.216 ms | inside range |
| delivery p99 | 32.089-34.433 ms | 47.061 ms | 45.133 ms | 36.063 ms | +4.7% |
| ack p99 | 40.169-48.846 ms | 62.815 ms | 58.451 ms | 49.523 ms | +1.4% |
| all-delivered p99 | 36.674-44.887 ms | 58.471 ms | 54.757 ms | 45.231 ms | +0.8% |
| server work CPU | 0.499671-0.499824 | 0.499612 | 0.499869 | 0.499982 | +0.03% |
| deliveries/s | 9,993.4-9,996.5 | 9,992.2 | 9,997.4 | 9,999.6 | better |

The structural result reduces shared delivery p99 by 20.1% versus the first
fast path. Across the 16 operation-throughput cells, three telemetry profiles,
and both pre-MCP draws (96 comparisons), final deltas range from -12.3% to
+19.9%; no operation-throughput cell regresses beyond the documented 15%
run-to-run band.

A read-only audit of all comparable DBZZ paths found 6/340 runtime-default,
9/340 exporter, and 6/339 disabled nonzero paths more than 15% adverse versus
both baseline draws. They are isolated readiness/tail-latency or short CPU
samples. No path repeats across all three profiles; the two paths that repeat
in two profiles have no greater-than-15% throughput regression. This is not a
formal gate override, but it does not show a consistent family-level MCP
regression.

Before the structural change, a temporary same-source diagnostic at `452e23d`
compared the ordinary invocation path with a direct call-site ablation. On the
first shared update, last delivery fell from 43.29 to 36.44 ms (-15.8%) and
acknowledgement from 47.55 to 40.39 ms. That isolated capability/context
construction at the invocation seam and led to replacing the generic helper
with structural branches at the four execution owners. The instrumentation is
absent from every commit and from the final canonical source bundle.
