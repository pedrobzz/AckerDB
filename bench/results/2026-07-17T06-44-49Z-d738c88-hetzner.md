## Correctness outcome

DBZZ and SpacetimeDB recorded no validation failure. All five failures belong
to the Convex local development backend:

| Case | Recorded failure |
| --- | --- |
| shared fixed rate | 1,168 duplicate and 6,660 unexpected deliveries |
| shared capacity, 32 writers | 932 duplicate and 6,660 unexpected deliveries |
| shared capacity, 50 writers | 236 duplicate deliveries |
| partitioned fixed rate | 196 unexpected deliveries |
| partitioned capacity, 500 writers | eight shown one-second mutation timeouts, 196 unexpected deliveries, and 42 failed requests in total |

Convex reached a recorded 2.72 GiB backend RSS peak and left only about 24 MiB host
memory available during this leg. The kernel did not report an OOM kill and the
harness continued to SpacetimeDB. This repeats the known conclusion that this
3.7-GiB host cannot produce a valid all-system comparison at the default
500-user x 50-query shape. It would be wrong to evaluate performance acceptance
or use the invalid Convex subscription cells.

## DBZZ regression questions

### Shared fixed-rate CPU repeats

The exact within-run profile comparison reproduces the suspected CPU cost:

| Machine | Runtime default | Telemetry disabled | Default overhead |
| --- | ---: | ---: | ---: |
| Hetzner EPYC/Linux, `d738c88` | 0.9998 cores | 0.4997 cores | +100.1% |
| Apple M2 Pro/macOS, `c2b665a` | 0.2920 cores | 0.1498 cores | +95.0% |

The absolute core values are not cross-machine comparable. The repeatable
signal is the within-run ratio: default telemetry approximately doubles server
CPU in this fixed-rate case on both machines. Exporter and runtime-default CPU
on Hetzner were effectively identical (0.9996 versus 0.9998 cores), so this is
not an exporter-specific cost.

### Mutation profile direction repeats

Runtime-default mutation throughput was below telemetry-disabled throughput in
all eight mutation/profile cells:

| Evidence | Runtime-default deficit versus disabled |
| --- | ---: |
| Hetzner EPYC/Linux, `d738c88` | 15.2%-34.0% across 8/8 cells |
| Apple M2 Pro/macOS, `c2b665a` | 13.8%-27.3% across 8/8 cells |

Again, absolute throughput cannot be compared across these machines or Bun
builds (`d738c88` used stable Bun; `c2b665a` used an M2 Pro and Bun canary).
The consistent within-run direction does repeat. The explicit exporter versus
runtime-default comparison on Hetzner was mixed, from -11.3% to +12.1%, so it
does not show a systematic exporter penalty beyond normal +/-15% run noise.

## Most relevant same-host comparison

The prior `95783c3` current-host log used the same host and operation profiles,
but reduced subscriptions to 100 users x 20 queries and stopped the connection
ladder at 500. Operation throughput and the shared 1/100/500 connection levels
remain directly useful; subscription numbers do not share the same offered
shape.

| DBZZ area | `d738c88` versus prior same-host log |
| --- | --- |
| query throughput, 4 profiles | +3.7%, +9.3%, +12.2%, +12.3% |
| uncontended mutation throughput, 4 profiles | +24.7%, +41.4%, +51.8%, +47.8% |
| contended mutation throughput, 4 profiles | +37.7%, +37.9%, +32.8%, +51.2% |
| procedure throughput, 4 profiles | -13.5%, -28.3%, -29.4%, -25.8% |
| connection query throughput at 1/100/500 | -2.4%, +13.2%, +9.7% |

Mutation performance is materially better than the prior same-host evidence,
despite the still-large telemetry-disabled gap. Procedure throughput is the
opposite signal: three loaded profiles regress well beyond the documented
15% noise band and deserve investigation or a confirming same-host rerun before
claiming the branch has no runtime regression.

DBZZ remained 14.2x-29.5x faster than Convex for query and mutation throughput
cells in this run. Procedure throughput was only 3.73x-4.77x Convex, below the
repository's 5x policy floor, but the all-system acceptance cannot be evaluated
because Convex correctness failed.

## Interpretation

- The benchmark runner behaved correctly: measured failures were saved instead
  of aborting the whole run, while malformed performance claims were withheld.
- The full small-host result does not clear Issue 15 performance acceptance.
- It does clear the diagnostic question: the shared fixed-rate telemetry CPU
  ratio and the all-eight mutation default-versus-disabled direction both
  reproduce on independent hardware.
- The default workload still exceeds this host's valid Convex capacity. A
  reduced same-host comparison can answer DBZZ-versus-Convex margins, but it is
  not a substitute for the canonical frozen M2 acceptance workload.
